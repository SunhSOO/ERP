# GAILAB 브랜딩 및 메일 품질 개선 설계

## 목적

사용자에게 보이는 제품명을 GAILAB으로 바꾸고, 메일 첨부 다운로드·상세 보기의 오류를 바로잡으며, 프로젝트 맥락을 활용한 메일 분류 추천을 제공한다.

## 범위와 제약

- 사용자 화면과 사용자 문서의 `Luminode` 표기를 `GAILAB`으로 변경한다. 현재 운영 중인 Docker Compose 프로젝트명, 이미지명, 컨테이너명, 데이터 볼륨명, `LEP_*` 환경 변수와 서버 폴더는 변경하지 않는다.
- 새 메일은 항상 `unclassified`로 유지한다. 추천은 관리자의 승인과 상태 전이를 대체하지 않는다.
- 관리자만 공용 미분류 검토함과 승인·제외를 수행한다. 승인된 프로젝트 메일은 관리자 또는 해당 프로젝트 생성자만 본다.
- 실제 업무 메일을 테스트·분류·승인하지 않는다. migration과 기존 승인 상태를 변경하지 않는다.
- API의 기존 `MailOut` 소비자를 깨지 않도록 추천 관련 필드는 선택적으로 추가한다.

## 1. GAILAB 브랜딩

웹 메타데이터, 로그인·공용 레이아웃, 사용자용 README와 화면에 노출되는 브랜드 문구를 `GAILAB`으로 바꾼다. 패키지명 `@lep/*`, Python 모듈 `lep`, Compose의 `luminode` 식별자와 이미지 태그는 운영 안정성을 위해 그대로 둔다.

## 2. 첨부 파일명과 확장자 보존

백엔드는 안전하게 정리한 원본 파일명을 RFC 5987 `filename*=UTF-8''...` 형식으로 `Content-Disposition`에 넣는다. 웹의 다운로드 프록시는 이 헤더를 값 변경 없이 전달한다. 헤더가 없는 경우에만 `attachment`를 사용한다.

회귀 테스트는 한글 이름과 `.pdf`, 공백이 든 이름과 `.xlsx`를 각각 검증한다. 프록시 테스트는 업스트림 헤더 보존을, API 테스트는 안전한 헤더 인코딩을 검증한다.

## 3. 메일 상세 접근 오류

목록에서 선택한 메일의 상세 조회는 백엔드의 actor·메일함·프로젝트 범위 검사를 최종 권한 판단으로 사용한다. 프런트엔드는 목록 상태와 상세 상태가 순간적으로 달라지는 경우에 자체 검증 때문에 정상 선택을 `forbidden`으로 바꾸지 않는다.

다만 목록 밖의 드라이브 딥링크는 기존처럼 상세 응답의 ID, `classification=project`, 현재 프로젝트 ID 및 `linked_file_id`를 다시 확인한다. 이는 다른 메일함에서 재사용된 UIDL과 다른 프로젝트의 첨부 접근을 막기 위한 검사다. 실제 403은 오류 원인을 유지해 표시한다.

회귀 테스트는 관리자가 미분류 목록에서 메일을 선택하는 경우, 프로젝트 생성자가 자기 프로젝트의 승인 메일을 선택하는 경우, 다른 프로젝트와 미분류 메일에 대한 거부를 각각 포함한다.

## 4. 프로젝트 맥락 기반 추천

### 추천 입력

각 미분류 메일의 발신 도메인, 제목, 본문 앞부분, 현재의 의도 키워드·마일스톤 코드를 다음 프로젝트 정보와 비교한다.

- 프로젝트 코드와 이름
- 고객사명
- 프로젝트의 마일스톤 코드
- 같은 프로젝트에서 이미 승인된 메일의 제목·의도·마일스톤 코드

초기 구현은 외부 LLM 호출이나 임베딩 저장소 없이 결정적 점수 방식으로 시작한다. 이는 운영 환경마다 LLM 가용성이 달라도 추천 결과가 재현되고, 메일 본문을 새 외부 서비스에 보내지 않기 위함이다.

### 결과와 화면

각 후보는 프로젝트 ID, 관련도(`high`/`medium`/`low`), 매칭 근거의 짧은 목록을 가진다. 가장 높은 후보만 기존 `suggested_project_id`에 호환성 있게 반영하고, 새 `suggestions` 배열은 검토 화면에 최대 세 후보를 보인다. 동점 또는 근거 없는 점수는 추천하지 않는다.

메일 상세의 승인 폼은 최고 추천 프로젝트를 기본 선택으로 표시하되 사용자가 바꿀 수 있다. 목록은 추천 프로젝트와 관련도를 표시하고, `추천 있음`/`추천 없음` 필터를 제공한다. 추천은 DB 상태·감사 로그·버전·idempotency를 바꾸지 않는다.

### 권한과 데이터 경계

추천 계산은 mail application service에서 `projects.public`의 읽기 전용 인터페이스를 통해 프로젝트 정보를 가져온다. projects 테이블을 직접 쓰지 않으며 기존 승인된 메일의 mail-owned 리뷰 테이블은 읽기 전용으로 사용한다. 추천 결과는 응답 시 계산하며 새 테이블이나 migration을 만들지 않는다.

## 오류 처리

- 원본 첨부 없음·체크섬 불일치·권한 없음은 현재 HTTP 상태를 유지하고 파일로 내려보내지 않는다.
- 추천 계산 실패는 메일 목록과 승인 기능을 막지 않는다. 해당 메일은 `suggestions=[]` 및 기존 도메인 추천이 있을 때만 `suggested_project_id`를 보인다.
- 추천 후보가 현재 존재하지 않거나 접근 불가한 프로젝트를 가리키면 후보에서 제외한다.

## 검증

- 백엔드 단위·API 테스트: 첨부 헤더, 상세 권한 경계, 프로젝트 맥락 점수 및 동점·근거 없음·도메인 추천 호환성.
- 프런트 테스트: 목록 선택 후 상세 표시, 거부 메시지, 추천 표시·필터·기본 프로젝트 선택, 한글 다운로드 헤더 전달.
- 전체 메일 테스트, TypeScript, lint, Next production build, 해당 백엔드 테스트를 실행한다.
- 배포 전 운영 서버의 관련 파일을 백업하고, 새 API·웹 컨테이너만 재빌드한 후 health/ready를 확인한다.

## 제외 항목

- 자동 승인·자동 프로젝트 배정
- 기존 승인 메일의 다른 프로젝트 이동
- Docker/볼륨/서버 디렉터리 이름 변경
- 실제 업무 메일에 대한 대량 재분류 또는 기존 데이터 backfill
